# R36S 性能瓶颈深挖复盘（2026-09-30）

> 起点：真机闹市区 fps 26-33，"感觉性能没完全发挥出来"。
> 终点：瓶颈画像完整落定，可做的都做完了，其余是地基限制。
> 本轮产物：音频泄漏修复（保留）、VAO 开启（保留）、perf 工具链（保留）；
> GPU timer query / draw trace / fp16 实验（全部回退，结论存档于此）。

## 1. 测量工具链（本轮搭起来的家底）

| 工具 | 位置 | 用途 |
|---|---|---|
| perf | 真机 `/usr/bin/perf`（apt 装 linux-perf，6.12.107） | CPU 热点采样，硬件 cycles 事件可用 |
| PerfHud | 引擎自带（reVC.ini `[Perf] PerfHud=1` 开启） | 屏幕 HUD + 每 120 帧一行 `[perf]` 日志 |
| gdb 采样脚本 | 真机 `/tmp/sample_prof.sh` | poor man's profiler（perf 装好前的替代） |
| strace -c | 系统自带 | syscall 计数与耗时分布 |

不可用的：ARM Streamline / Mali GPU Inspector（内核 4.4 无 panfrost PM 计数器接口）、
ftrace（需手配 root）。Mali kbase debugfs 有 mali0 节点但无性能计数器。

## 2. 瓶颈画像（闹市区 dc≈440，fps 28）

```
一帧 35ms 的去向:
  CPU 提交   20-22ms  ← 主线程一半时间在 libmali blob 内部（perf: 48.6% self）
  swap 等待  ~15ms    ← 其中 ~10ms 是 KMS 合成器固定节奏（空场景实测同样 10ms）
  GPU 真忙    ~6ms    ← timer query 实测，不是瓶颈
```

关键证据链：

1. **退出瞬间（dc=11 空场景）gpu 墙钟仍 10.29ms**，而 timer query 的 swap 段只有
   0.06ms → swap 等待 = 显示节奏（buffer 轮换影子 vsync），`VSync=0` 也躲不掉。
2. **perf 主线程采样 2081 样本**：libmali 48.6% / 引擎 41.8% / libc 3.8%。
   blob 内部热点极度分散（最大单函数 1.16%）——不是某函数慢，是**调用太频繁**。
3. **strace 5 秒账本**：futex 45.7%（1628 次，均值 523μs——主线程睡在 blob CMAR
   队列同步上）；ioctl 仅 1.5%（6087 次，4μs/次——kbase 内核通道飞快）。
4. **引擎侧已无水分**：`setRasterStageOnly`/`setFilterMode`/`setAddressU/V` 全有
   脏检查；`flushUniforms` 有 serialNum 脏标记；uniform 只在变化时上传。

## 3. 与树莓派的架构对比（源码实锤）

树莓派 Mesa V3D（`mesa/src/gallium/drivers/v3d/`）：
```c
cl_emit(&job->bcl, TILE_BINNING_MODE_CFG, config) {...}   // 纯内存写 (v3d_cl.h:217)
ret = v3d_ioctl(v3d->fd, DRM_IOCTL_V3D_SUBMIT_CL, &job->submit);  // 整帧一次 ioctl (v3d_job.c:713)
```
每 draw = 往 DMA buffer 写几十字节，**每帧 1 次 syscall**。这就是树莓派上
"GPU 时间测不出、完全并行"的原因。

R36S Mali blob：主线程 GL 调用 → CMAR 命令队列（跨线程 + 信号量背压）→
`mali-cmar-backe` 线程消费 → kbase。**每批同步点** × 440 draws/帧
× 每 draw 6-8 个 GL 调用 = 主线程 48% 时间在 blob。

**换 panfrost 不可行**：Mesa 用户态支持 G31（`pan_model.c:82`），
但真机内核 **4.4.189**，panfrost 需 5.2+（Bifrost 支持需 5.8+）。
换内核 = 换系统，不现实。

## 4. Draw trace 合并度分析（决定不做合批）

工具：librw 侧 per-draw 状态元组记录（raster/alphatest/alpha/blend），
`gl3DrawTraceReport` 输出切换数与可合并 run，`gl3DrawTraceRasters` 输出
distinct 纹理直方图（top1/top4）。已随 revert 移除，数据存档：

```
[batch] draws=217 texsw=200(92%) mergeable=16(7%) | distinct_tex=125 top1=18 top4=50
```

- 纹理重复率 = 217/125 = **1.74 draws/纹理**（排序有收益的判据是 >3）
- 原因：`Renderer.cpp:455-500` 建筑列表按世界扫描序提交，纹理随机交替
- 结论：排序后 texsw 200→125 但 draw 数不变，blob 同步点数才是主菜，
  收益撑死 1-2ms。**跨模型纹理图集**是唯一治本方案（周级工程，不做）

## 5. 试过并回退的

| 实验 | 结果 | 原因 |
|---|---|---|
| fp16（shaderDecl310es 全局 mediump） | **画质炸 + 帧率无提升** | blob 的 GLES 实现对 mediump 的处理不如预期；GPU 本来只忙 6ms，砍半也不解帧率瓶颈 |
| GPU timer query（swap 段也测） | 数据拿到后回退 | 运行时开销（每帧 3-4 个 query 对象）与价值不匹配 |
| draw trace | 数据拿到后回退 | 同上 |

VAO（`RW_GL_USE_VAOS`）保留：+1ms 提交收益，画面无异常，无风险。

## 6. 最终结论

fps 28-33 的天花板 = **Mali blob 跨线程命令提交固定成本 × 440 draws**
+ **KMS 合成器 10ms 节奏**。GPU 算力（~6ms 真忙）与引擎侧状态管理都不是瓶颈。
应用侧可做的已到顶；突破需要纹理图集（大工程）或换内核上 panfrost（换系统）。

真机现状：`reVC` = ASTC 全量 + 音频泄漏修复（c6640a2e）+ FONT_LOCALE +
匿名信号量 + VAO，PerfHud=0，备份 `reVC.fontlocale.bak` / `reVC.nosro.bak`。
