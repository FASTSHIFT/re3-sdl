# 05 - 文字渲染管线架构分析：Details/RenderState 双状态模型缺陷

> 状态：分析完成，待讨论定方案
> 基线：`92bcace3`（菜单偶数串修复 + hang 修复 + 图标空白修复已部署）
> 结论先行：**当前所有视觉 bug（变细/无阴影、双 Y、HUD 排版乱）共享同一个架构根因——渲染回放阶段读取"当前全局状态"而非"提交时快照"。** 补丁式修复在此架构上不可收敛，建议按 §5 方案重构。

---

## 1. 管线全貌

reVC 的文字渲染是**两段式：提交（Submit）→ 回放（Replay）**，中间隔着一个共享扁平缓冲区：

```
游戏代码                      提交阶段                        回放阶段（当帧稍后）
─────────                    ─────────                       ──────────────────
SetScale/SetFontStyle/
SetColor/SetDropShadow...    PrintString(6参)
  ↓ 全部写入 Details  ───→     ① 把 Details 快照进           RenderFontBuffer()
                               CFontRenderState 结构          ① Sprite[RenderState.style].SetRenderState()
TheText.Get() → wchar*         ② 逐字符拷贝进                ② 扫 buffer，遇 '\0' 段边界就
                               FontRenderStateBuf               换载下一段快照到 RenderState
                               （token 原样拷入）             ③ 每字符：PrintChar + advance
                                                             ④ 遇 token：ParseToken 副作用
```

关键数据结构：

| 变量 | 类型 | 生命周期 | 设计意图 |
|---|---|---|---|
| `CFont::Details` | `CFontDetails`（全局单例） | "当前设置"，跨帧存活 | 游戏代码的状态机 |
| `CFontRenderState` | 逐段快照（style/scale/color/slant/...） | 随 buffer 存活一帧 | 回放时还原提交时状态 |
| `CFont::RenderState` | `CFontRenderState`（全局单例） | "正在回放的段"的快照 | 回放上下文 |
| `FontRenderStateBuf` | 1KB 扁平字节流 | 一帧 | 字符与快照交错存放 |

**这就是屎山的源头**：回放阶段本应只读 `RenderState`（快照），但代码里到处直接读 `Details`（全局）。两条状态线在回放时**竞态交错**，谁先谁后全看当帧提交顺序。

## 2. 实测证据（GDB，PC 本地复现）

### 2.1 "性能显示变细/后几个字阴影没了" —— scale 竞态实锤

GDB 断点 `PrintChar`，条件 `Details.style != RenderState.style || Details.scaleX != RenderState.scaleX`：

```
MISMATCH#1 D.style=3 R.style=3 D.sx=0.900 R.sx=1.500 x=1141.5 y=27.3
MISMATCH#2 D.style=3 R.style=3 D.sx=0.900 R.sx=1.500 x=1177.5 y=27.3
MISMATCH#3 D.style=3 R.style=3 D.sx=0.900 R.sx=1.500 x=1213.5 y=27.3
（主菜单标题"主菜单"，24 次命中，D.sx=0.9 vs R.sx=1.5）
```

**解读**：`主菜单` 标题提交时 scale=1.5（快照正确），但回放跑到 `PrintChar` 时，全局 `Details.scaleX` 已经被**下一项**（菜单条目，scale=0.9）改掉。而 `PrintChar` 的 CJK 分支里：

```cpp
// Font.cpp PrintChar CJK 分支（92bcace3 现状）
CSprite2d::AddToBuffer(
    CRect(x, y,
        x + CJK_DRAWW * Details.scaleX,    // ← 读全局！应为 RenderState.scaleX
        y + CJK_DRAWH * Details.scaleY),   // ← 同上
    RenderState.color,                     // ← 颜色却读快照
    ...);
```

**几何用 0.9、颜色用 1.5 段的颜色**——同一段绘制里两个状态源混用。这解释了：
- **"变细"**：CJK quad 宽度按 0.9 算，但字距 advance 按快照 1.5（`RenderFontBuffer` 831 行 `textPosX += RenderState.scaleX * GetCharacterWidth(c)`）→ 字形窄、间距宽、视觉发虚；
- **"后几个字阴影没了"**：CJK 分支的**阴影 quad**（PrintChar 内 `Details.dropShadowPosition != 0` 时附加绘制）用 `Details.dropShadowPosition`——回放时它已被下一个提交者清零/改值，阴影时有时无，逐字抖动；
- **"动画期间正常、稳定后变细"**：菜单切换动画期 `FadeIn` 每帧改 alpha，各条目的 SetScale 调用被动画代码重排，提交-回放间隔小；动画结束进入稳态后，标题段与条目段同帧提交、flush 在最后，标题回放时 Details 已是条目的 scale——竞态窗口稳定打开。

### 2.2 "两个 Y" —— token 的三处重复消费

`(Y)` 图标链路：GXT 存 `~k~VEHICLE_ENTER_EXIT~`（全字符带 0x8000 标志）→ `CMessages::InsertPlayerControlKeysInString` 在**入队前**把键名替换为 `~T~`（**纯 ASCII**，来自 XboxButtons 表）→ 串里混着"带标志 token + ASCII token"。

消费点竟有**三处**，且互不知情：

| # | 位置 | 时机 | 对 `~T~`（ASCII） | 对带标志 token |
|---|---|---|---|---|
| 1 | `PrintString`(6参) 提交循环 | 入 buffer 时 | 单参 `ParseToken(s)`：**副作用设置 PS2Symbol、NewLine、Details.color**，然后把 token 字符原样拷入 buffer | 只判 `'~'`，**整个 token 被当普通字符拷入**（字母 h/k/w 全进 buffer） |
| 2 | `RenderFontBuffer` 回放循环 | 出 buffer 时 | 4参 `ParseToken`：再次副作用 + `DrawButton` 画图标 | 92bcace3 加的手动消费：跳字符 + 部分副作用 |
| 3 | `GetStringWidth`/`GetNextSpace`/`GetNumberLines` | 布局测量时 | 各自跳 token 计宽 | 92bcace3/e20c6858 改过，逻辑与 1/2 不一致 |

两个 Y 的直接成因（部署版 92bcace3）：
- 提交点#1 对 ASCII `~T~` 调单参 ParseToken → `PS2Symbol = BUTTON_TRIANGLE`（**残留，无人清**）；
- 回放点#2 又遇到 `~T~` → 4参 ParseToken → `PS2Symbol` 再设 → `DrawButton` 画第 1 个 Y；
- **阴影 pass**（PrintString 提交时先入阴影段再入正文段，两段都含 `~T~`）→ 阴影段回放时又画一次 → 第 2 个 Y（偏移 dropShadow 位置）。
- 间距大：`textPosX += RenderState.scaleY * 17.0f` 只在图标后加一次，但 `~T~` 的闭 `~` 之后循环尾 `pStr++` 再多吃一个字符的 advance（off-by-one，ParseToken 返回已越过闭 `~`，循环再 `++` 跳过下一个真字符）。

### 2.3 "HUD 排版乱"

HUD 计时/时钟是**纯 ASCII 数字**，但菜单/中文模式下同帧还有别的 CJK 提交。回放时：
- `GetCharacterWidth`（1415 行）判定用 `Details.style`/`RenderState.style` **混合**（同一函数里两种都出现）；
- ASCII 数字走到 `Size[0][RenderState.style][c]`——若 `RenderState.style` 恰是 FONT_JAPANESE（3），查的是**第 3 号字体的西文宽度表**，与实际绑定的纹理（`Sprite[RenderState.style]`）错配 → 数字间距错乱。
- 另外 CJK 分支判定 `IsJapaneseFont()` = `IsJapanese() && Details.style == FONT_JAPANESE`——**用 Details 而非 RenderState**，段快照 style=STANDARD 的 ASCII 数字段，若此刻 Details.style=JAPANESE，PrintChar 走 CJK 几何（半宽图集）→ 数字变细。

## 3. 缺陷总账（按严重度）

| # | 缺陷 | 位置（92bcace3） | 影响 |
|---|---|---|---|
| A1 | PrintChar CJK 几何/阴影读 `Details.scaleX/scaleY/dropShadowPosition/dropColor` | 610-640 | 变细、阴影丢失、逐字抖动 |
| A2 | `IsJapaneseFont()` 读 `Details.style`，回放上下文应为 `RenderState.style` | Font.h:243 | 段级字体错配（数字半宽/汉字走西文表） |
| A3 | `GetCharacterWidth/Size` 混用 `Details.style` 与 `RenderState.style` | 1414-1464 | advance 与字形来源不一致 → 间距乱 |
| A4 | RenderFontBuffer 开头 `Sprite[RenderState.style]` 用的是**上一帧遗留**的 RenderState（先 SetRenderState 后才装载首段快照） | 696-699 | 首段绑定错纹理（帧首） |
| B1 | token 消费三处实现，提交/回放/测量互不一致 | 711/845-875/测量族 | 双 Y、空白、宽度错 |
| B2 | 单参 ParseToken 在提交阶段留 `PS2Symbol` 残留，无人清 | 516/765 | 悬空图标 |
| B3 | 回放循环 off-by-one：ParseToken 返回后循环 `pStr++` 多吃一字符 | 760-766 | 图标后间距大、偶发吃字 |
| C1 | `RenderState.style != Details.style` 才 flush——**scale/color 改变不触发 flush** | 888-891 | 不同 scale 的段共享快照外的全局态 |
| C2 | 阴影 pass 靠临时改写全局 `Details` 再递归（dropShadowPosition=0、bIsShadow=true）再还原 | 894-916 | 递归期间任何读取 Details 的代码看到中间态 |
| C3 | `FontRenderStateBuf` 1KB 无越界保护（提交循环直接写） | 918 | 长文本潜在越界 |

## 4. 为什么补丁修不动

我们三轮补丁（e20c6858 → 92bcace3）分别打在 测量/布局、token 消费、死循环保护 上——**每一处都默认"回放时 Details 仍然是提交时的值"**，这个前提在稳态下不成立（GDB 2.1 已证）。在 A1-A4 未解决前：

- 修 A1（PrintChar 改读 RenderState）→ 立刻暴露 A4（首段 Sprite 绑定错）；
- 修 A2（IsJapaneseFont 改 RenderState）→ 提交阶段（布局测量）也在调它，那时必须读 Details——**同一个函数被两个阶段用不同语义调用**；
- B 族每修一处，另两处的步进/副作用假设就变化（两个 Y 正是 B1+B2+B3 叠加）。

**结论：这不是 bug 是架构。** 上游 re3-VC 同样有此模型，但日文原版从不把 ASCII 段和 CJK 段混排在同一帧同 scale 变化场景里大规模使用，所以上游"能跑"。我们的中文管线把混排变成常态，竞态从偶发变成必现。

## 5. 方案（供讨论）

### 方案甲：快照补全（小改，风险低，预计 1-2 天）
原则：**回放路径只读 RenderState，提交路径只读 Details**。

1. `CFontRenderState` 增加 `dropShadowPosition`、`dropColor` 字段；提交时快照（A1）；
2. `IsJapaneseFont()` 拆成两个：`IsJapaneseFontCurrent()`（Details，提交/测量用）与 `RenderStateIsJapaneseFont()`（RenderState，PrintChar/回放截断/token 判定用）（A2）；
3. `GetCharacterWidth/Size` 回放路径统一走 RenderState.style 的专用变体（A3）；
4. `RenderFontBuffer` 先装载首段快照再 `Sprite[...].SetRenderState()`（A4，两行对调）；
5. token 三处统一为一个 `ConsumeToken(ptr, mode)`，mode 区分 提交拷贝/回放副作用/测量跳过；回放循环 off-by-one 用"返回停在闭 `~` 上，循环 ++ 自然越过"约定消除（B1/B3）；
6. 提交阶段入口清 `PS2Symbol`（B2）。

### 方案乙：渲染上下文对象（中改，风险中，预计 3-4 天）
回放循环里构造局部 `const CFontDetails replayCtx`（由段快照还原），PrintChar/GetCharacterWidth 全部改签名收 `const CFontDetails&`，全局 Details 只服务提交。等于把方案甲的类型安全做满，顺带解决 C1（scale/color 变化也触发 flush：快照不等即 flush）。

### 方案丙：放弃延迟回放，立即渲染（大改，不推荐）
PrintString 直接 AddToBuffer，绕开缓冲。改动面最大，丢掉原版"批量提交减少状态切换"的性能特性，对 R36S 低端 GPU 不利。

**我的建议：甲先行**（能立刻消掉 A/B 全部可见症状），乙作为后续技术债偿还（C1/C2/C3 一并解决）。丙否决。
